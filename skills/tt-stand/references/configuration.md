# Настройка tt-stand

Профили доступа, файл конфигурации, учётные данные и область видимости namespace.
Краткий порядок первого запуска — в [скилле](../SKILL.md).

## Настройка

```text
tt-stand config init
```

Команда создаёт корневой файл `~/.tt-stand/config.json` и профиль `default`.
Существующий файл без `--force` перезаписывается только после подтверждения в терминале.
Без подтверждения и без терминала файлы не меняются, команда завершается с кодом 0,
а ответ называет существующие файлы. Перезаписать без вопроса — `--force`.

`tt-stand config init --profile investigation` создаёт именованный профиль.
При первой настройке общий файл получает `defaultProfile: "investigation"`.
Если общий файл уже существует, его содержимое сохраняется. Профиль по умолчанию
задаётся полем `defaultProfile` в общем `config.json`.

По умолчанию общий файл и профили находятся в каталоге `~/.tt-stand`:

```text
~/.tt-stand/
  config.json                      корневые настройки
  profiles/<имя>/profile.json      настройки профиля
  profiles/<имя>/credentials.json  учётные данные профиля
  profiles/<имя>/journal/          журнал вызовов профиля
```

Профиль объединяет доступ к Grafana, кластеру и MongoDB для одного контура,
филиала или стенда. К профилю обращаются по имени. В нём заполняются разделы
для нужных источников. Команда, которой нужна незаполненная часть профиля,
завершается с `profile_incomplete`.

Действующий профиль определяется в порядке приоритета:

1. флаг `--profile <имя>`;
2. переменная окружения `TT_STAND_PROFILE`;
3. поле `defaultProfile` в корневом `config.json`.

Если ни один источник профиль не назвал, а профиль в установке ровно один,
используется он без указания. Если профилей несколько, а выбора нет — отказ
`profile_ambiguous` с перечнем имён; молчаливого выбора первого попавшегося
не бывает. Если названный профиль не существует — отказ `profile_missing`.
Имя действующего профиля видно в успешном ответе команды, использующей профиль, в поле `echo.profile`.

Если в `profiles` нет каталогов профилей, а корневой `config.json` содержит
`grafana`, `kubernetes` или `repositoryRoots`, он читается как профиль `default`.

### Первичная настройка

Порядок для того, кто устройством профилей не пользовался:

1. `tt-stand config init` — создаёт корневой `config.json` и профиль `default`
   с пустым файлом `~/.tt-stand/profiles/default/credentials.json`.
2. Открыть `~/.tt-stand/profiles/default/profile.json` и вписать адрес Grafana полем
   `grafana.baseUrl`: генератор его не заполняет, а без него команды логов и метрик
   отвечают `profile_incomplete`.
3. Открыть указанный в ответе файл `credentials.json` и вписать доступ к Grafana
   от руки: логин с паролем либо токен.
4. Проверить состояние командой `tt-stand config profiles` — она называет, что
   в профиле настроено и заполнен ли файл учётных данных, не раскрывая значений.
5. Проверить доступ к Grafana командой `tt-stand env` — она возвращает список
   namespace из хранилища логов. Доступ к кластеру проверяется отдельно,
   командой `tt-stand k8s pods`.

Если что-то пошло не так, класс ошибки называет следующий шаг:

| Класс ошибки             | Что делать                                                                                         |
| ------------------------ | -------------------------------------------------------------------------------------------------- |
| `credentials_missing`    | файла доступа нет по указанному пути — владелец создаёт его вручную                                |
| `credentials_incomplete` | в файле не хватает обязательного значения для выбранного способа доступа — дописать его            |
| `auth_failed`            | Grafana отвергла логин, пароль или токен — проверить, что значения верны и не истекли              |
| `profile_incomplete`     | в профиле нет целого раздела доступа, нужного вызванной команде — дописать раздел в `profile.json` |

Kubeconfig выбирается в порядке: `kubernetes.kubeconfig` в `profile.json` действующего
профиля, затем `KUBECONFIG`, затем `~/.kube/config`. Команда `config init` записывает
`kubernetes.kubeconfig` явно, поэтому для использования `KUBECONFIG` это поле нужно удалить.

```json
{
  "kubernetes": {
    "kubeconfig": "~/.kube/fictional-cluster.yaml"
  }
}
```

Путь может вести в каталог. Если внутри ровно один файл `.yaml`, `.yml`, `.json` или
`config`, используется он. При нескольких файлах ответ перечисляет кандидатов и
предлагает задать один путь явно; автоматического выбора нет.

Окружение записи — это namespace. Для прикладного лога он читается из плоского поля
`kubernetes.pod_namespace`. Для ingress namespace определяется по upstream: из списка,
который вернуло хранилище логов, берётся самое длинное имя namespace, после
которого идёт дефис, либо полное совпадение. Kubernetes в этом механизме не используется.

Список и время его получения показывает команда:

```text
tt-stand env
```

Порядок списка сохраняется как в ответе хранилища. `env` запрашивает список без периода
и лимита с учётом заданной области namespace. Команды логов запрашивают список без
этой фильтрации, если среди полученных записей есть upstream без собственного namespace.

Несопоставленный upstream, включая HTTP-адрес, получает метку `unknown` рядом с исходным
значением и неизменённой записью.

## Файл конфигурации

Корневой файл расположен в `~/.tt-stand/config.json`. Путь к общему файлу задаётся
аргументом `--config <путь к config.json>` или переменной окружения `TT_STAND_CONFIG`.
Аргумент важнее переменной.
Если при чтении настроек явно заданный файл отсутствует, инструмент возвращает `config_invalid`
и называет полный путь и источник. `config init` может создать файл по этому пути.

Формат — JSON: он разбирается самим Node без зависимостей и надёжно правится
инструментами вроде `jq`.

В корневом `config.json` общие настройки включают:

| Поле             | Тип    | Умолчание | Что делает                                                                                                                                                                      |
| ---------------- | ------ | --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `defaultProfile` | строка | поля нет  | профиль, который используется, если не назван флагом или переменной окружения; имя `default` записывает `config init`, а без поля действует правило «профиль один — берётся он» |

```json
{
  "defaultProfile": "default"
}
```

Доступ к Grafana и кластеру задаётся в `profile.json` каждого профиля:

| Поле                           | Тип                | Умолчание                                      | Что делает                                                                                                                                                                                                                                                                                                                                                                                              |
| ------------------------------ | ------------------ | ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `grafana.baseUrl`              | строка, URL        | нет                                            | базовый адрес Grafana                                                                                                                                                                                                                                                                                                                                                                                   |
| `grafana.credentialsFile`      | строка, путь       | `credentials.json` в каталоге профиля          | файл с доступом к Grafana                                                                                                                                                                                                                                                                                                                                                                               |
| `grafana.timeoutSeconds`       | число > 0          | нет                                            | таймаут одного HTTP-запроса. Без него таймаута нет вовсе                                                                                                                                                                                                                                                                                                                                                |
| `grafana.datasourceUid`        | строка             | нет                                            | закрепить источник логов. Без поля берётся первый источник подходящего типа, а все найденные названы в пояснении ответа; поле нужно, чтобы выбор не зависел от порядка, и когда список источников недоступен учётной записи                                                                                                                                                                             |
| `grafana.metricsDatasourceUid` | строка             | нет                                            | закрепить источник метрик. Источник ищется отдельно от источника логов, тем же способом: первый источник, чей тип входит в перечень `prometheus`, `victoriametrics-metrics-datasource`, `victoriametrics-datasource` — типы посредника, отдающего HTTP API Prometheus; без поля берётся первый подходящий, а все найденные названы в эхе ответа. Источник логов выбирается независимо от этой настройки |
| `kubernetes.kubeconfig`        | строка, путь       | `KUBECONFIG`, затем `~/.kube/config`           | путь к kubeconfig. Может вести в каталог                                                                                                                                                                                                                                                                                                                                                                |
| `kubernetes.context`           | строка             | контекст, объявленный в kubeconfig действующим | имя контекста, если kubeconfig описывает несколько кластеров                                                                                                                                                                                                                                                                                                                                            |
| `namespaceScope`               | список строк       | нет (ограничения нет)                          | образцы имён namespace, которые инструмент показывает — раздел «Область видимости»                                                                                                                                                                                                                                                                                                                      |
| `repositoryRoots`              | список строк, пути | пусто                                          | каталоги с локальными копиями репозиториев, нужны команде `image`                                                                                                                                                                                                                                                                                                                                       |
| `journal.directory`            | строка, путь       | каталог `journal` внутри каталога профиля      | каталог журнала вызовов этого профиля                                                                                                                                                                                                                                                                                                                                                                   |

Если среди источников Grafana не нашлось ни одного нужного типа, команда отказывает
классом `datasource_not_found`: текст называет перечень допустимых типов и саму
настройку, которой источник задаётся явно, — `grafana.datasourceUid` для источника
логов, `grafana.metricsDatasourceUid` для источника метрик.

Пустая строка, значение `.` или значение `..` в `grafana.datasourceUid` или
`grafana.metricsDatasourceUid` — не то же самое, что отсутствие поля: инструмент
не считает такую настройку незаданной, а отказывает классом `config_invalid`,
называя профиль и поле — такое значение нельзя закодировать сегментом пути
`/api/datasources/proxy/uid/<uid>/`.

Команда `config init` создаёт следующий `profile.json` профиля `default`.

```json
{
  "grafana": {
    "credentialsFile": "~/.tt-stand/profiles/default/credentials.json"
  },
  "kubernetes": {
    "kubeconfig": "~/.kube/config"
  },
  "repositoryRoots": [],
  "journal": {
    "directory": "~/.tt-stand/profiles/default/journal"
  }
}
```

Неверный тип любого поля даёт `config_invalid` с указанием профиля и поля. Файла
в расположении по умолчанию может не быть — инструмент работает со значениями
по умолчанию.

Доступ к Grafana хранится отдельно, в `credentials.json` того же профиля. Поле
`kind` называет способ доступа `basic` с полями `login` и `password` либо
`token` с полем `token`. Файл содержит JSON, базовый URL задаётся в `grafana.baseUrl` профиля.

```json
{
  "kind": "basic",
  "login": "readonly",
  "password": "секрет"
}
```

```json
{
  "kind": "token",
  "token": "секрет"
}
```

В `credentials.json` лежит только доступ. Базовый адрес Grafana задаётся в
`profile.json`, полем `grafana.baseUrl`.

## Область видимости

Профиль может задавать поле `namespaceScope` — список образцов имён namespace,
которые инструмент готов показывать:

```json
{
  "namespaceScope": ["stand-*", "qa-*"]
}
```

Образец сопоставляется с именем namespace целиком, единственный символ
подстановки — `*` (заменяет любую последовательность символов, включая пустую),
сравнение чувствительно к регистру.

Перечень разрешающий: namespace попадает в область, только если совпал хотя бы
с одним образцом; показывается только совпавшее. Без поля `namespaceScope`
ограничения нет — видно всё, что доступно доступом профиля.

Команды, принимающие namespace параметром (`k8s pods`, `k8s log`, `k8s events`,
`k8s history`, `k8s get`), учитывают его внутри области, а не вместо неё: заданный
`--namespace` действует как пересечение с образцами области. Запрошенный этими
командами namespace вне области — отказ `namespace_out_of_scope`, а не пустой
результат: пустота неотличима от «событий не было», а именно такую путаницу
область и должна предотвращать. Текст отказа называет действующий профиль,
запрошенный namespace и образцы области. Namespace умолчания, который команда
кластера получает без флага, эта же проверка не обходит — подробно ниже.

Логи и метрики параметра `--namespace` не принимают, поэтому класса
`namespace_out_of_scope` не получают: их результат при заданной области
фильтруется инструментом, а не отклоняется отказом — как именно, описано
ниже в этом разделе.

Команды кластера, вызванные без `--namespace`, работают с namespace, объявленным
действующим в kubeconfig. Он проверяется на область наравне с именем, заданным
флагом: умолчание не способ обойти область. Поэтому вызов без флага при контексте,
чей namespace вне области, отказывает — и текст отказа говорит, что имя взято
из умолчания, а не названо в команде. Ресурсы уровня кластера, у которых namespace
нет по природе вида, областью не ограничиваются.

Выражение запроса область не трогает. Ограничение уходит в хранилище отдельным
параметром, предназначенным для сужения выдачи подмножеством логов, поэтому
выражение с конвейером остаётся работоспособным, а обойти ограничение вложенным
подзапросом нельзя: хранилище применяет его и к подзапросам.

Эхо каждого ответа называет применённые образцы (поле `namespaceScope`) и число
записей, не попавших в ответ из-за области (поле `recordsOutOfScope`). Выражение
запроса эхо показывает дословно таким, каким его дал пользователь.

Для метрик область действует иначе, потому что HTTP API Prometheus не имеет
стандартного параметра серверной фильтрации по namespace: выражение уходит на сервер
без изменений, а область инструмент применяет сам к полученным рядам по стандартной
метке Kubernetes `namespace`. Ряд с меткой `namespace` вне области и ряд без этой
метки вообще (например, сумма без группировки по namespace либо одиночное значение `scalar`) не выводятся; оба случая
учтены отдельно в эхе и в причинах неполноты. Ответ `metrics series` фильтруется так
же — набор меток ряда проверяется тем же способом. Значения метки `namespace`
(`metrics labels --label namespace`) фильтруются по области как имена namespace;
значения любой другой метки при заданной области не выводятся, потому что их
принадлежность namespace по такому ответу не определяется — эти значения видны
вместе с namespace в ответе `metrics series`.

**Область — это предохранитель от невнимательности, а не защита.** Права на чтение
namespace выдаёт кластер и Grafana, а не клиент: `namespaceScope` лишь сужает то,
что показывает инструмент, при уже имеющемся доступе. Обойти область можно правкой
`profile.json` или обращением к тем же данным сторонним клиентом — от этого поле
не защищает и не должно.

Учётные данные для подключения хранятся в `credentials.json` профиля.
Неизвестные флаги отклоняются, их значения исключаются из вывода и журнала.

## MongoDB через SSH

Для MongoDB профиль содержит словарь `servers` с записями `ssh` и `mongodb`.
Настройки Grafana и Kubernetes находятся в разделах `grafana` и `kubernetes`.
Пример использует вымышленные адреса.

```json
{
  "servers": {
    "ssh": {
      "kind": "ssh",
      "host": "bastion.example.invalid",
      "port": 22,
      "username": "investigator",
      "privateKeyPath": "~/.ssh/id_ed25519",
      "knownHostsPath": "~/.ssh/known_hosts"
    },
    "mongodb": {
      "kind": "mongodb",
      "uri": "mongodb://database.example.invalid:27017/?authSource=admin",
      "sshServer": "ssh",
      "defaultDatabase": "shop",
      "timeoutSeconds": 30
    }
  }
}
```

SSH использует ключ по `privateKeyPath` и проверяет сервер по `knownHostsPath`. MongoDB
подключается к адресам со стороны SSH-сервера. Таймаут по умолчанию 30 секунд.
SSH `timeoutSeconds` ограничивает подключение, MongoDB `timeoutSeconds` ограничивает
весь вызов с чтением всех порций. Допустимо конечное число больше нуля и не больше 2147483.647 секунды.
URI MongoDB исключает учётные данные и секретные параметры TLS `passphrase`, `key`, `pfx`
и `tlsCertificateKeyFilePassword`.
У команды `mongo` флаг `--database` выбирает базу для одного вызова, а `--server`
выбирает MongoDB-сервер. Единственный сервер MongoDB выбирается автоматически.
При нескольких серверах команда требует явного выбора. Без `--database`
используется `defaultDatabase` выбранного сервера.

В `credentials.json` рядом с профилем добавляются записи по именам MongoDB и SSH.
Если в файле уже настроен доступ Grafana, его поля `kind` и поля выбранного способа доступа сохраняются.
Ниже показаны только добавляемые записи.

```json
{
  "ssh": { "passphrase": "" },
  "mongodb": { "username": "", "password": "" }
}
```

Владелец заполняет значения. Агент проверяет настройки через
`tt-stand config --profile investigation --json` и выполняет запросы через
`tt-stand mongo --profile investigation --query-file request.json`.
Чтение профиля, credentials и приватного ключа выполняет инструмент.
Правила агента запрещают прямое чтение этих файлов и изменение заполненных значений.

## Просмотр настроек и профиль по умолчанию

`config --json` показывает эффективные настройки и признаки заданности секретов.
Профиль по умолчанию задаётся полем `defaultProfile` общего `config.json`.
Путь общего файла задаётся через `--config` либо `TT_STAND_CONFIG`.
Профиль выбирается через `--profile`, `TT_STAND_PROFILE`, `defaultProfile` либо как
единственный доступный.
Передавай профиль явно в каждом вызове расследования. При нескольких серверах MongoDB
добавь `--server <имя>`. Список и заполненность показывает
`tt-stand config profiles`, эффективные значения и источники показывает
`tt-stand config --profile <имя> --json`.

## Область видимости в работе агента

Область — свойство профиля, а не аргумента команды: она действует сама в каждом запросе.
Дублировать условие области в самом запросе не нужно и вредно: собственное условие агента
сужает выборку внутри области, но не расширяет её и не заменяет.

Отказ `namespace_out_of_scope` означает выход за область профиля, а не отсутствие событий.
Правильная реакция — сообщить человеку об ограничении профиля,
а не подбирать другой запрос к тому же namespace.

Часть уже полученных записей тоже может не попасть в ответ, если их namespace вне области.
Это мягче: причина неполноты называется прямо, признак неполноты истинен, код завершения
нулевой.

Для метрик область работает иначе: HTTP API Prometheus не принимает параметр,
которым сервер сам ограничил бы выдачу набором namespace, поэтому выражение уходит
на сервер без изменений, а область инструмент применяет сам к полученным рядам —
по метке `namespace`. Ряд с namespace вне области и ряд без метки namespace вообще
(например, сумма без группировки либо одиночное значение `scalar`) в ответ не попадают; для ряда без метки причина
неполноты предлагает добавить в выражение группировку `by (namespace)`. То же
относится к `metrics series`. Значения метки `namespace` из
`metrics labels --label namespace` фильтруются по области как имена namespace;
значения любой другой метки при заданной области не выводятся — их принадлежность
namespace смотри через `metrics series`.

## Первичная настройка

1. Выполни `tt-stand config init` для создания профиля `default` и общего файла
   с `defaultProfile`. Для отдельного именованного профиля используй `config init --profile <имя>`.
2. Покажи владельцу пути и состав полей из `references/configuration.md`.
   Grafana настраивается в `grafana`, Kubernetes — в `kubernetes`.
   Для MongoDB добавляются `servers.<имя>` видов `ssh` и `mongodb`, включая пути
   SSH-ключа и known_hosts. Секреты SSH и MongoDB находятся под именами серверов
   в `credentials.json`. Файл заполняет владелец.
3. После заполнения вызови `tt-stand config --json` или `tt-stand config --profile <имя> --json`
   для безопасной проверки значений и их источников. `tt-stand config profiles` показывает список профилей
   и состояние заполненности файлов доступа.
4. Проверь доступ через нужную команду. Для Grafana выполни `env`, для Kubernetes
   `k8s pods`, для MongoDB передай документ `{"ping":1}` через `mongo --query-file`.
5. По желанию владельца настрой `repositoryRoots` для определения локальных веток по образу.

| Класс                                           | Действие                                                             |
| ----------------------------------------------- | -------------------------------------------------------------------- |
| `credentials_missing`, `credentials_incomplete` | назвать владельцу путь файла и необходимые поля                      |
| `auth_failed`                                   | сообщить, что значения не приняты Grafana, не подбирать их перебором |
| `profile_incomplete`                            | назвать профиль и недостающую часть настроек                         |
| `ssh_host_key_invalid`                          | сообщить владельцу о несоответствии known_hosts                      |
| `ssh_auth_failed`, `mongo_auth_failed`          | сообщить владельцу о непринятых значениях доступа                    |

Настройки профиля правит агент по прямому указанию человека. Файл `credentials.json`
заполняет человек сам. Заполненный профиль и ключ используются через tt-stand.

## Запреты

Агенту запрещено:

- читать напрямую профиль, читать и выводить содержимое `credentials.json` и приватного SSH-ключа;
- изменять заполненный профиль, ключ и known_hosts без прямой просьбы владельца;
- записывать в него значения;
- передавать логин, пароль или токен доступа Grafana аргументом команды;
- повторять в своём ответе значение доступа, присланное человеком.

Прислал человек доступ в переписке — назови путь файла и попроси вписать самому, не повторяя
присланное.

Чтобы узнать, заполнен ли файл, используй `tt-stand config profiles`: команда отвечает признаком заполненности, а не содержимым файла.

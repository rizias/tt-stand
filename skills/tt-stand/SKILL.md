# tt-stand — расследование по логам и Kubernetes

Инструмент снимает механику доступа к хранилищу логов и Kubernetes и отдаёт данные
как есть: ничего не скрыто, не заменено и не обрезано. Исключение одно — область
видимости namespace, если она задана в профиле: в ответ попадают только данные
разрешённых namespace, а число исключённого ею названо в `echo`.

Он не порождает вариантов значения, не режет период, не подставляет лимитов
и таймаутов, не сортирует записи и не разворачивает «значение → идентификатор».
Всё это делаешь ты.

## Команды

```text
tt-stand logs query  (--query <LogsQL> | --query-file <путь>) --start <время> --end <время> [--limit N]
tt-stand logs search --value <значение> [--value ...] --start <время> --end <время> [--limit N]
tt-stand logs http [--query <LogsQL> | --query-file <путь> | --value <значение> [--value ...]] --start <время> --end <время> [--limit N]
tt-stand logs fields --field <имя> --start <время> --end <время> [--query <LogsQL> | --query-file <путь>] [--limit N]
tt-stand metrics query   (--query <PromQL> | --query-file <путь>) --start <время> --end <время> [--step <шаг>]
tt-stand metrics instant (--query <PromQL> | --query-file <путь>) [--time <время>]
tt-stand metrics labels  [--label <имя>] [--match <селектор> ...] [--start <время>] [--end <время>]
tt-stand metrics series  --match <селектор> [--match ...] [--start <время>] [--end <время>]
tt-stand token [--value <токен>]
tt-stand k8s get <ресурс> [--namespace <ns>] [--name <имя>]
tt-stand k8s log <под> [--namespace <ns>] [--container <имя>] [--previous]
tt-stand k8s events [--namespace <ns>]
tt-stand k8s pods [--namespace <ns>]
tt-stand k8s history <рабочая нагрузка> [--namespace <ns>]
tt-stand image <образ или тег>
tt-stand env
tt-stand config init [--force]
tt-stand config profiles
tt-stand init [путь к проекту] [--for claude,agents]
tt-stand update
```

Общие флаги: `--human`, `--config <путь>`, `--profile <имя>`. Время — RFC 3339 либо
относительное, например `--start -2d --end now`; значения уходят как даны.

## Передача выражения запроса

Выражение со знаками `<`, `>`, `|`, `&`, `^`, `%` или кавычками передавай через
`--query-file <путь>`, а не через `--query`: запиши подготовленное выражение в файл
и укажи путь к нему. Правило одинаково для Windows, macOS и Linux и для любой
оболочки — PowerShell, cmd.exe, bash, zsh: каждая оболочка по-своему трактует эти
знаки, и без файла запрос доходит до сервера искажённым либо не доходит вовсе.
Выражение без таких знаков можно передавать флагом `--query`, как раньше.

Обёртка `tt-stand.cmd` эту задачу не решает: она передаёт аргументы через
интерпретатор команд Windows (cmd.exe), а он трактует те же знаки как свои — в какой
бы оболочке `tt-stand.cmd` ни была вызвана, включая PowerShell и bash. Называй
`tt-stand.cmd` только способом обойти запрет PowerShell на сценарии `.ps1`, а не
способом передать выражение со специальными знаками.

При «команда не найдена» проверь установку, PATH и доступ к файлу: изолированная среда
агента может не иметь прав на установленную у пользователя программу. Отказ доступа
не исправляется переустановкой; используй разрешённый средой механизм запуска.
Отказ доступа возможен и для сети, и для записи журнала; его тоже не исправляют повтором.

Сверяй `echo.query` с подготовленным выражением: оболочка может изменить кавычки
и специальные символы даже без знаков из списка выше. Такой ответ относится
к изменённому запросу, а не к задуманному.

## Сначала проверь ответ

| Поле | Что проверить |
|---|---|
| `incomplete` | при `true` прочитай все `incompleteReasons`; пустые `data` не доказывают отсутствие событий |
| `echo` | запрос, период, лимит, порядок сервера; для Kubernetes — kubeconfig, контекст, кластер, namespace, ресурс, фактический GET |
| `echo.ignoredFlags` | непустой перечень значит, что переданный флаг эта команда не применяет: он не повлиял на результат — команда выполнилась так, как будто флага не было |
| `summary.byEnvironment` | `unknown` означает, что namespace записи определить не удалось |
| `errorClass` | разбирай по классу, а не по совпадению русского текста |

**При `hitLimit: true` теряется ранняя часть периода.** Хранилище отдаёт самые свежие
записи, поэтому вывод «это случилось впервые тогда-то» на усечённом результате неверен.
Для полного охвата раздели период на части без пропусков и проверь каждую.
Увеличение лимита допустимо, если запрос посилен хранилищу. С VictoriaLogs 1.36.0 конец
периода в выборку не входит, и части с общей границей не пересекаются; на более ранних
версиях запись на границе может прийти дважды. Если часть не получена, назови
непроверенный интервал.
«Первое» и «последнее» событие устанавливаются только в пределах проверенного периода.

## Причины неполноты

| Причина в `incompleteReasons` | Что означает |
|---|---|
| записей пришло ровно столько, сколько лимит | за лимитом могут быть ещё; ранняя часть периода потеряна |
| часть строк ответа не разобрана | нечитаемые строки пропущены, их число в `echo.unparsableLines` |
| для части записей namespace не определён | они помечены `unknown`, исходное значение рядом |
| список namespace из хранилища получить не удалось | разметка окружений не выполнена |
| значений пришло ровно столько, сколько лимит | инвентаризация поля неполна |
| получение данных прервано | в ответе только успевшая часть |
| сервер вернул ответ без тела | это не то же самое, что «ничего не найдено» |
| команда не отработала | запрос не выполнялся или оборвался до первой записи |
| команда прервана | в `data` только записи, успевшие прийти до обрыва |
| команда Kubernetes не отработала | запрошенное состояние кластера не получено |
| состав кластера прочитан не полностью | часть групп API недоступна; они названы в `echo.unavailableSources` |
| ревизий ReplicaSet не найдено | история выкаток недоступна — не то же самое, что выкаток не было |
| часть записей не попала в ответ | их namespace вне области профиля; число в `echo.recordsOutOfScope` |
| сервер пометил ответ частичным (isPartial) | сервер метрик сам отметил, что ответ неполон |
| сервер вернул предупреждения | тексты — в `summary.server.warnings` |
| часть рядов не попала в ответ: их namespace вне области видимости профиля | это не то же самое, что отсутствие данных |
| ряды без метки namespace не показаны | их принадлежность области не проверить — группировка `by (namespace)` в выражении даст проверяемые ряды |
| часть значений метки namespace не попала в ответ | они вне области видимости профиля — это не то же самое, что отсутствие данных |
| значения метки не показаны | при заданной области их принадлежность namespace не определяется — `metrics series` показывает значения вместе с namespace; в самом ответе к причине дописано число скрытых значений |
| ответ сервера неожиданного вида показан не целиком | при заданной области принадлежность namespace его частей не проверить |
| тег не содержит полного SHA | коммит по такому образу не определяется |
| локальный репозиторий не найден | коммит и ветки по нему не определялись |
| коммит отсутствует локально | ссылки могли устареть; `git fetch` инструмент не выполняет |
| часть копий скилла не поставлена | причины в `data.skipped`, поставленные копии в `data.installed` |

## Порядок поиска

Сначала дешёвый фильтр по формам значения, и только если он не дал ответа — дорогое
выражение вроде регулярного. Обратный порядок опасен вдвойне: дешёвый фильтр по одной
форме даёт пустой результат, неотличимый от полного, а дорогое выражение на широком
периоде упирается в таймаут.

Выбирай период относительно исследуемого события. Для широкого периода используй
известные избирательные признаки (идентификатор ошибки, namespace, контейнер, точная
фраза), когда они соответствуют задаче, и называй цель охвата. Если нужен полный обзор,
сохраняй его охват, при необходимости разделяя период.

Сообщай подтверждённые находки и оставшиеся пробелы в ходе долгой работы.
Если для продолжения не хватает сведений, уточни у пользователя недостающий ориентир:
что уже проверено и что позволит узнать его ответ. Пустые части периода сами по себе
не повод прекращать проверку заданного периода. Используй поправку для пересмотра
поиска; не проси повторять известное.

## Расследование «кто менял сущность»

1. Найди значение всеми формами через повторяемый `--value`.
2. Если запрос действия содержит только ID, найди запись, где значение и ID встречаются
   вместе, назови её источник и повтори поиск по идентификатору. Если такой записи нет
   или связь неоднозначна, вывод неполон: уточни недостающие сведения у пользователя;
   пустой поиск значения не доказывает отсутствия действий по сущности.
3. Ищи через `logs http`: исходный `record` остаётся целиком, `http` добавляет метод, путь,
   статус, клиент, User-Agent, upstream и `tokens`. `http: null` не отбрасывай, сверяй
   `summary.httpUnparsed`.
4. Читай весь `http.tokens[].payload` — утверждение может лежать во вложенной структуре.
   `source` показывает `address` или `outside_address`.
5. Отдельный токен раскрывай через `tt-stand token`. Сверь header, payload, `issuedAt`,
   `expiresAt`, `signatureVerified: false`.
6. Вывод формулируй как «токен утверждает, что действие выполнил …»: подпись не проверялась,
   личность не установлена.
7. Если для ответа нужны сведения о сервисе или кластере, сопоставляй время с
   `k8s events`, `k8s pods`, логом пода; контекст, кластер и namespace сверяй по `echo`.

## Варианты написания значения

Словесный фильтр режет строку по небуквенно-цифровым символам, поэтому одна форма даёт
правдоподобный пустой ответ, пропустив URL-кодированную.

| Тип | Формы для самостоятельной проверки |
|---|---|
| Телефон `+70000000000` | `+70000000000`, `70000000000`, `%2B70000000000`, `2B70000000000`, `80000000000`, `0000000000` |
| Почта `person@example.invalid` | исходная, `person%40example.invalid`, нужный регистр, локальная часть |
| UUID | исходный, без дефисов, нужный регистр |

**Пример.** Исходная строка журнала:

```text
10.0.0.1 - - "GET /users/?query=%2B70000000000 HTTP/1.1" 200 919 "-" "Mozilla/5.0"
```

Вызов:

```text
tt-stand logs search --value '+70000000000' --value '%2B70000000000' --start <начало> --end <конец>
```

Фактический ответ: `recordsReturned: 1`, `incomplete: false`.
Ожидаемый вывод: значение встречается в URL-кодированной форме; поиск только по исходной
вернул бы ноль записей и выглядел бы полным.

**Пример нарезки периода.** В вымышленном журнале две записи:

```json
{"_time":"2026-01-15T10:05:00Z","kubernetes.pod_namespace":"demo","_msg":"example-event"}
{"_time":"2026-01-15T10:35:00Z","kubernetes.pod_namespace":"demo","_msg":"example-event"}
```

Вызов:

```text
tt-stand logs search --value example-event --start 2026-01-15T10:00:00Z --end 2026-01-15T11:00:00Z --limit 1
```

Фактический ответ на этих данных: запись в 10:35, `recordsReturned: 1`,
`hitLimit: true`, `incomplete: true`. Для полного охвата выполни оба запроса:

```text
tt-stand logs search --value example-event --start 2026-01-15T10:00:00Z --end 2026-01-15T10:30:00Z --limit 2
tt-stand logs search --value example-event --start 2026-01-15T10:30:00Z --end 2026-01-15T11:00:00Z --limit 2
```

Каждая часть возвращает одну запись, `hitLimit: false`, `incomplete: false`.
Ожидаемый вывод: обе записи получены, исходный час покрыт целиком. Размер частей
и лимиты здесь иллюстративные.

## Окружение и namespace

**По умолчанию поиск идёт по всем окружениям сразу** — сужаешь ты, не инструмент. Каждая
запись помечена окружением, распределение в `summary.byEnvironment`.

Окружение равно namespace. Есть поле `kubernetes.pod_namespace` — окружение берётся оттуда;
нет — разбирается upstream и выбирается самый длинный namespace-префикс из списка хранилища.
Список и время его получения даёт `tt-stand env`. HTTP-адрес upstream остаётся `unknown`.

У общего входного сервера namespace записи может отличаться от окружения приложения.
Назначение HTTP-запроса проверяй по `http.upstream` и связанным логам приложения.
Фильтр по месту записи для вымышленного namespace `demo`:

```text
tt-stand logs query --query 'kubernetes.pod_namespace:="demo"' --start 2026-01-15T10:00:00Z --end 2026-01-15T11:00:00Z
```

Он не включает логи общего входного сервера из другого namespace.

## Kubernetes

| Задача | Как |
|---|---|
| Прочитать ресурс | `k8s get` принимает plural, singular, short name или `resource.group`; `--name` переключает на один объект |
| Разрешить неоднозначность | взять кандидата `resource.group` из ответа |
| Найти причину перезапуска | `k8s events`, затем `k8s log <под> --previous`, затем `k8s history <нагрузка>` |
| Связать перезапуск с выкаткой | совпадение времени перезапуска с новой ревизией в `k8s history` |

Kubeconfig берётся из настроек профиля, затем `KUBECONFIG`, затем стандартного пути.
Пустой перечень ревизий помечает ответ неполным: история недоступна, а не выкаток не было.
`previous_log_unavailable` — физическая утрата лога, а не пустой лог.
Состояние ресурсов получено на момент запроса, а не на момент исторического события.
Окружение, видимое в логах, не обязательно доступно выбранному Kubernetes-контексту.

## Кто нагружает окружение

1. Возьми ряд потребления ресурса по подам за период командой `metrics query`
   с группировкой `by (namespace, pod)`, например
   `sum(rate(container_cpu_usage_seconds_total{namespace="<namespace>"}[5m])) by (namespace, pod)`.
   Группировка без `namespace` не даёт ряда, проверяемого по области видимости
   профиля, — при заданной области такой ряд не будет показан.
2. Найди под, чей ряд заметно отличается от остальных, — он кандидат на источник
   нагрузки.
3. Прочитай логи этого пода за тот же период: `k8s log <под> --namespace <namespace>`
   либо `logs query` с фильтром по namespace и имени пода.
4. Если под принимал запросы через общий входной сервер, подними записи входного
   сервера о запросах к нему за тот же период командой `logs http`: адрес клиента,
   программа клиента (`User-Agent`) и `upstream` — в поле `http`.

Выбирай шаг (`--step`) и период так, чтобы число точек ряда не превышало предел,
который допускает сервер метрик: слишком мелкий шаг на длинном периоде сервер
отклонит. При отказе с классом `metrics_query_rejected` читай текст сервера
целиком — он и называет причину, включая превышенный предел.

## От контейнера к рабочей нагрузке

Имя контейнера, которое встречается в логе, не является именем рабочей нагрузки —
у контейнера и у управляющего им Deployment или ReplicaSet разные имена. Владелец
пода называется полем `metadata.ownerReferences` самого пода —
`tt-stand k8s get pods --name <под>`; если владелец — ReplicaSet, у него то же поле
называет владеющий Deployment. Если сборщик логов сам пишет владельца пода в запись
лога, рабочую нагрузку можно взять оттуда, не запрашивая под отдельно. Имя контейнера
в `k8s history` не передавай — команда принимает имя рабочей нагрузки, а не контейнера.

## Какой код выкачен

```text
tt-stand k8s pods --namespace <ns>          # в ответе images каждого пода
tt-stand image <образ из ответа выше>       # версия, коммит, ветки-кандидаты
```

`summary.resolved: false` — коммит не определён, причина в `summary.reason`: сторонний образ
без SHA, нет локальной копии репозитория, коммита нет локально. Это не ошибка команды.

`branchCandidates` — кандидаты, а не ответ: один коммит входит в несколько веток.
`echo.refsUpdatedAt` показывает возраст локальных ссылок; `git fetch` инструмент не делает,
поэтому пустой перечень веток может означать устаревшую копию.

## Классы ошибок

| `errorClass` | Действие |
|---|---|
| `bad_request` | ошибка в аргументах вызова, а не отказ внешней системы |
| `credentials_missing`, `credentials_incomplete` | проверить файл доступа профиля |
| `auth_failed`, `datasource_list_forbidden`, `datasource_not_found` | проверить доступ или идентификатор источника |
| `timeout_client` | проверить заданный таймаут; сузить запрос или разделить период, сохранив нужный охват |
| `upstream_error`, `stream_aborted` | проверить ошибку и полноту; для долгого запроса уменьшить объём одной части; сам код 502 не устанавливает причину отказа |
| `metrics_query_rejected` | прочитать текст сервера целиком — он называет причину: ошибку в выражении или превышение предела точек либо рядов, а не отказ авторизации; отказ в доступе (HTTP 401 или 403) даёт `auth_failed`, а не этот класс, даже если тело ответа похоже на ошибку запроса |
| `config_invalid`, `config_exists` | исправить поле или путь к явно заданному файлу; `config_exists` — файл появился во время `config init`, повторить команду |
| `profile_missing`, `profile_ambiguous`, `profile_incomplete` | выбрать существующий профиль или дописать недостающую часть |
| `namespace_out_of_scope` | запрошенный namespace вне области профиля |
| `token_invalid` | проверить compact-формат и JSON header и payload |
| `kubeconfig_missing` | задать путь одним из трёх способов |
| `kubeconfig_ambiguous` | выбрать один файл из `data.candidates` |
| `kubeconfig_invalid`, `kube_context_missing` | исправить файл или контекст |
| `k8s_access_forbidden` | запросить read-only доступ на ресурс |
| `k8s_resource_not_found` | проверить имя через discovery |
| `k8s_resource_ambiguous` | использовать `resource.group` |
| `k8s_upstream_error` | разобрать текст ответа API и фактический GET |
| `pod_not_found` | проверить namespace и имя пода |
| `previous_log_unavailable` | зафиксировать утрату и искать централизованный журнал |
| `git_unavailable` | установить git либо добавить его в PATH |
| `skill_copy_skipped` | причины по копиям в `data.skipped` |

Без `grafana.timeoutSeconds` у tt-stand нет собственного таймаута HTTP-запроса.
Если оболочка вернула идентификатор продолжающейся команды, получи её итоговый ответ
или явно останови ненужный запрос. Окончание ожидания оболочки не означает отказ
tt-stand: не запускай дубликат и сообщай пользователю о долгом ожидании.

## Выбор профиля

Профиль — самостоятельный контур настроек и доступа. Порядок выбора: флаг
`--profile <имя>`, переменная окружения `TT_STAND_PROFILE`, поле `defaultProfile`
корневого файла настроек. Единственный профиль берётся без указания.

Несколько профилей без выбора — отказ `profile_ambiguous`, а не выбор первого попавшегося.
Указан несуществующий — `profile_missing`.

Какие контуры настроены, показывает `tt-stand config profiles`. Пользуйся ею вместо чтения
файлов настроек: она называет профили, не раскрывая учётные данные.

## Область видимости

Область — свойство профиля, а не аргумента команды: она действует сама в каждом запросе.
Дублировать условие области в самом запросе не нужно и вредно: собственное условие агента
сужает выборку внутри области, но не расширяет её и не заменяет.

Отказ `namespace_out_of_scope` означает выход за область профиля, а не отсутствие событий.
Правильная реакция — сообщить человеку об ограничении профиля,
а не подбирать другой запрос к тому же namespace.

Часть уже полученных записей тоже может не попасть в ответ, если их namespace вне области.
Это мягче: причина неполноты называется прямо, признак неполноты истинен, код завершения
нулевой.

Для метрик область работает иначе: HTTP API Prometheus не принимает параметр,
которым сервер сам ограничил бы выдачу набором namespace, поэтому выражение уходит
на сервер без изменений, а область инструмент применяет сам к полученным рядам —
по метке `namespace`. Ряд с namespace вне области и ряд без метки namespace вообще
(например, сумма без группировки либо одиночное значение `scalar`) в ответ не попадают; для ряда без метки причина
неполноты предлагает добавить в выражение группировку `by (namespace)`. То же
относится к `metrics series`. Значения метки `namespace` из
`metrics labels --label namespace` фильтруются по области как имена namespace;
значения любой другой метки при заданной области не выводятся — их принадлежность
namespace смотри через `metrics series`.

## Первый запуск

```text
npm install --global @rizias/tt-stand
tt-stand init
```

`init` ставит скилл в каталоги проекта: `.claude/skills` (Claude Code) и `.agents/skills`
(Codex, OpenCode). Без аргументов спрашивает, какие из них; без вопроса —
`tt-stand init <путь к проекту> --for claude,agents`. Без подтверждения ничего не пишется.
Настройка доступа — раздел «Первичная настройка» ниже.

## Обновление

Если tt-stand при запуске сообщил о новой версии — выполни `tt-stand update` и продолжай.
Копии скилла обновятся сами при следующем запуске.

## Первичная настройка

1. `tt-stand config init` — создаёт профиль и файл учётных данных.
2. Назови человеку путь `credentials.json` действующего профиля и состав: поле `kind`
   со значением `basic` (тогда `login` и `password`) либо `token` (тогда `token`).
   Дальше файл заполняет человек сам; дождись этого.
3. `tt-stand config profiles` — покажет состояние профиля и заполненность файла доступа,
   не раскрывая значений.
4. `tt-stand env` — проверит фактический доступ.
5. По желанию: `tt-stand image` называет ветки по коммиту только через локальные копии
   репозиториев. Если у человека они есть, спроси родительский каталог, внутри которого
   лежат репозитории с именами образов, и впиши его в `repositoryRoots`. Если копий или
   доступа к репозиториям нет, шаг пропускается: команда отдаёт версию и SHA из тега,
   а сведения о коммите и ветки не определяет и помечает ответ неполным.

Для каждого отказа своё действие, а не повтор попытки:

| `errorClass` | Действие агента |
|---|---|
| `credentials_missing`, `credentials_incomplete` | назвать человеку путь файла и недостающие значения, дождаться, пока он впишет их сам |
| `auth_failed` | сообщить человеку, что значения не приняты Grafana; не подбирать их перебором |
| `profile_incomplete` | назвать профиль и недостающую часть настроек |

Поля `profile.json`:

| Поле | Что означает | Где взять значение |
|---|---|---|
| `grafana.baseUrl` | базовый адрес Grafana | адрес, по которому человек открывает Grafana в браузере, без пути |
| `grafana.credentialsFile` | файл доступа; умолчание — `credentials.json` в каталоге профиля | задаётся, только если человек держит файл доступа в другом месте |
| `grafana.timeoutSeconds` | таймаут одного HTTP-запроса; без него таймаута нет | число секунд по решению человека |
| `grafana.datasourceUid` | закрепляет источник логов; нужен, когда подходящих источников несколько или учётной записи недоступен список источников | uid источника: в Grafana — Connections → Data sources → источник, uid в адресе страницы; все найденные источники названы в `echo.datasourceNote` ответа `logs` |
| `grafana.metricsDatasourceUid` | закрепляет источник метрик; нужен, когда подходящих источников несколько или учётной записи недоступен список источников; без поля берётся первый подходящий по типу | `echo.datasourceUid` ответа любой команды `metrics`; все найденные источники с типами — в `echo.datasourceNote`; либо в Grafana — Connections → Data sources → источник, uid в адресе страницы |
| `kubernetes.kubeconfig` | путь к kubeconfig, может вести в каталог; без поля — `KUBECONFIG`, затем стандартный путь | путь к файлу доступа к кластеру, который выдали человеку |
| `kubernetes.context` | имя контекста, если в kubeconfig их несколько | раздел `contexts` файла kubeconfig; действующий контекст назван в эхе команд `k8s` |
| `namespaceScope` | образцы имён namespace, которые инструмент показывает | задаёт человек; существующие имена — в ответе `tt-stand env` |
| `repositoryRoots` | каталоги с локальными копиями репозиториев для команды `image` | родительский каталог, где у человека лежат клоны репозиториев |
| `journal.directory` | каталог журнала; умолчание — `journal` в каталоге профиля | задаётся, только если человек хочет держать журнал в другом месте |

Настройки профиля правит агент по прямому указанию человека. Файл `credentials.json`
заполняет человек сам.

## Запреты

Агенту запрещено:

- читать и выводить содержимое `credentials.json`;
- записывать в него значения;
- передавать логин, пароль или токен аргументом команды;
- повторять в своём ответе значение доступа, присланное человеком.

Причина запрета на аргумент: вызов пишется в журнал целиком, поэтому значение, переданное
аргументом, останется в журнале открытым текстом.

Прислал человек доступ в переписке — назови путь файла и попроси вписать самому, не повторяя
присланное.

Чтобы узнать, заполнен ли файл, используй `tt-stand config profiles`: команда отвечает признаком заполненности, а не содержимым файла.

## Журнал вызовов

Каждый вызов, кроме `update`, пишется отдельным файлом в каталог журнала действующего профиля: время, вызов
целиком, ответ целиком. Делать ничего не нужно, путь показан в `echo.journal`.

Большой ответ читай через локальную обработку: сначала сводку, `echo`, полноту и нужные
поля, затем выбранные исходные записи целиком. Если вывод оболочки обрезан, используй
сохранённый ответ, проверив, что журнал создан. Сокращённое представление не заменяет
исходные данные; записи с `http: null` тоже могут содержать нужное доказательство.

Ведёшь расследование не один — выставь `TT_STAND_RUN` на всё расследование одним значением:
по нему твои вызовы отделяются от чужих, текущее значение в `echo.journalRun`.

Последовательность вызовов из журнала — готовый материал для повторения разбора. Неудачные
попытки полезны так же, как удачные: по ним видно, какой путь не сработал.

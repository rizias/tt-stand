# Настройка tt-stand

Профили доступа, файл конфигурации, учётные данные и область видимости namespace.
Краткий порядок первого запуска — в [README](../README.md).

## Настройка

```text
tt-stand config init
```

Команда создаёт корневой файл `~/.tt-stand/config.json` и профиль `default`.
Существующий файл без `--force` перезаписывается только после подтверждения в терминале;
без терминала команда отказывается с `config_exists` и ничего не меняет.

Всё, что относится к инструменту, лежит в каталоге `~/.tt-stand`:

```text
~/.tt-stand/
  config.json                      корневые настройки
  profiles/<имя>/profile.json      настройки профиля
  profiles/<имя>/credentials.json  учётные данные профиля
  profiles/<имя>/journal/          журнал вызовов профиля
```

Профиль — единица настройки доступа: связка «Grafana и кластер», к которой можно
обратиться по имени. Профилей может быть один или сотня — по одному на контур,
филиал или отдельный стенд. Профиль может описывать только Grafana, только кластер
или оба сразу; команде, которой нужна не описанная в профиле часть, отказывает
`profile_incomplete`, а не обращение к чужому контуру.

Действующий профиль определяется в порядке приоритета:

1. флаг `--profile <имя>`;
2. переменная окружения `TT_STAND_PROFILE`;
3. поле `defaultProfile` в корневом `config.json`.

Если ни один источник профиль не назвал, а профиль в установке ровно один,
используется он без указания. Если профилей несколько, а выбора нет — отказ
`profile_ambiguous` с перечнем имён; молчаливого выбора первого попавшегося
не бывает. Если названный профиль не существует — отказ `profile_missing`.
Имя действующего профиля всегда видно в эхе ответа, в поле `profile`.

**Совместимость.** Если каталога `profiles` нет, а доступ описан прямо в корневом
`config.json`, он читается как профиль `default`, и править ничего не нужно. Файл
учётных данных со строками `u=`, `p=` и `e=` тоже принимается.

### Первичная настройка

Порядок для того, кто устройством профилей не пользовался:

1. `tt-stand config init` — создаёт корневой `config.json` и профиль `default`
   с пустым файлом `~/.tt-stand/profiles/default/credentials.json`.
2. Открыть `~/.tt-stand/profiles/default/profile.json` и вписать адрес Grafana полем
   `grafana.baseUrl`: генератор его не заполняет, а без него команды логов отвечают
   `profile_incomplete`.
3. Открыть указанный в ответе файл `credentials.json` и вписать доступ к Grafana
   от руки: логин с паролем либо токен.
3. Проверить состояние командой `tt-stand config profiles` — она называет, что
   в профиле настроено и заполнен ли файл учётных данных, не раскрывая значений.
4. Проверить доступ к Grafana командой `tt-stand env` — она возвращает список
   namespace из хранилища логов. Доступ к кластеру проверяется отдельно,
   командой `tt-stand k8s pods`.

Если что-то пошло не так, класс ошибки называет следующий шаг:

| Класс ошибки | Что делать |
|---|---|
| `credentials_missing` | файла `credentials.json` нет по ожидаемому пути — создать его заново командой `config init` либо вручную |
| `credentials_incomplete` | в файле не хватает обязательного значения для выбранного способа доступа — дописать его |
| `auth_failed` | Grafana отвергла логин, пароль или токен — проверить, что значения верны и не истекли |
| `profile_incomplete` | в профиле нет целого раздела доступа, нужного вызванной команде — дописать раздел в `profile.json` |

Kubeconfig выбирается в порядке: `kubernetes.kubeconfig` в `profile.json` действующего
профиля, переменная `KUBECONFIG`, стандартный путь `~/.kube/config`.

```json
{
  "kubernetes": {
    "kubeconfig": "~/.kube/fictional-cluster.yaml"
  }
}
```

Путь может вести в каталог. Если внутри ровно один файл `.yaml`, `.yml`, `.json` или
`config`, используется он. При нескольких файлах ответ перечисляет кандидатов и
предлагает задать один путь явно; автоматического выбора нет.

Окружение записи — это namespace. Для прикладного лога он читается из плоского поля
`kubernetes.pod_namespace`. Для ingress namespace определяется по upstream: из списка,
который вернуло хранилище логов, берётся самый длинный префикс. Kubernetes в этом
механизме не используется.

Список и время его получения показывает команда:

```text
tt-stand env
```

Порядок списка сохраняется как в ответе хранилища. `env` запрашивает полный список
напрямую без периода и лимита. Команды логов делают тот же запрос только если среди
полученных записей есть ingress-upstream; для остальных наборов дополнительного
обращения нет.

Несопоставленный upstream, включая HTTP-адрес, получает метку `unknown` рядом с исходным
значением и неизменённой записью.

## Файл конфигурации

Расположение корневого файла: `~/.tt-stand/config.json`. Переопределяется аргументом
`--config <путь>` или переменной окружения `TT_STAND_CONFIG`; аргумент важнее переменной.

Формат — JSON: он разбирается самим Node без зависимостей и надёжно правится
инструментами вроде `jq`.

Корневой `config.json` содержит только то, что не относится ни к одному профилю
в отдельности:

| Поле | Тип | Умолчание | Что делает |
|---|---|---|---|
| `defaultProfile` | строка | поля нет | профиль, который используется, если не назван флагом или переменной окружения; имя `default` записывает `config init`, а без поля действует правило «профиль один — берётся он» |

```json
{
  "defaultProfile": "default"
}
```

Доступ к Grafana и кластеру задаётся в `profile.json` каждого профиля:

| Поле | Тип | Умолчание | Что делает |
|---|---|---|---|
| `grafana.baseUrl` | строка, URL | нет | базовый адрес Grafana |
| `grafana.credentialsFile` | строка, путь | `credentials.json` в каталоге профиля | файл с доступом к Grafana |
| `grafana.timeoutSeconds` | число > 0 | нет | таймаут одного HTTP-запроса. Без него таймаута нет вовсе |
| `grafana.datasourceUid` | строка | нет | закрепить источник логов. Без поля берётся первый источник подходящего типа, а все найденные названы в пояснении ответа; поле нужно, чтобы выбор не зависел от порядка, и когда список источников недоступен учётной записи |
| `kubernetes.kubeconfig` | строка, путь | нет | путь к kubeconfig. Может вести в каталог |
| `kubernetes.context` | строка | контекст, объявленный в kubeconfig действующим | имя контекста, если kubeconfig описывает несколько кластеров |
| `namespaceScope` | список строк | нет (ограничения нет) | образцы имён namespace, которые инструмент показывает — раздел «Область видимости» |
| `repositoryRoots` | список строк, пути | пусто | каталоги с локальными копиями репозиториев, нужны команде `image` |
| `journal.directory` | строка, путь | каталог `journal` внутри каталога профиля | каталог журнала вызовов этого профиля |

Файл `profile.json` профиля `default`, который создаёт `config init`:

```json
{
  "grafana": {
    "credentialsFile": "~/.tt-stand/profiles/default/credentials.json"
  },
  "kubernetes": {
    "kubeconfig": "~/.kube/config"
  },
  "repositoryRoots": []
}
```

Неверный тип любого поля даёт `config_invalid` с указанием профиля и поля. Файла
может не быть — инструмент работает со значениями по умолчанию.

Доступ к Grafana хранится отдельно, в `credentials.json` того же профиля. Поле
`kind` называет способ доступа: `basic` — с полями `login` и `password`, либо
`token` — с полем `token`. Прежний построчный файл со строками `u=` (логин),
`p=` (пароль) и `e=` (базовый URL) по-прежнему принимается и толкуется как `basic`;
какой из двух видов перед инструментом, определяется попыткой разбора JSON,
а не именем файла.

```json
{
  "kind": "basic",
  "login": "readonly",
  "password": "секрет"
}
```

```json
{
  "kind": "token",
  "token": "секрет"
}
```

В `credentials.json` лежит только доступ. Базовый адрес Grafana задаётся в
`profile.json`, полем `grafana.baseUrl`.

## Область видимости

Профиль может задавать поле `namespaceScope` — список образцов имён namespace,
которые инструмент готов показывать:

```json
{
  "namespaceScope": ["stand-*", "qa-*"]
}
```

Образец сопоставляется с именем namespace целиком, единственный символ
подстановки — `*` (заменяет любую последовательность символов, включая пустую),
сравнение чувствительно к регистру.

Перечень разрешающий: namespace попадает в область, только если совпал хотя бы
с одним образцом; показывается только совпавшее. Без поля `namespaceScope`
ограничения нет — видно всё, что доступно доступом профиля.

Запрос пользователя действует внутри области, а не вместо неё. Если пользователь
сузил выборку своим namespace, действует пересечение с областью. Если пользователь
выборку не сужал, она охватывает всю область профиля, а не всё, что доступно
учётной записи. Обращение к namespace вне области — отказ `namespace_out_of_scope`,
а не пустой результат: пустота неотличима от «событий не было», а именно такую
путаницу область и должна предотвращать. Текст отказа называет действующий
профиль, запрошенный namespace и образцы области.

Команды кластера, вызванные без `--namespace`, работают с namespace, объявленным
действующим в kubeconfig. Он проверяется на область наравне с именем, заданным
флагом: умолчание не способ обойти область. Поэтому вызов без флага при контексте,
чей namespace вне области, отказывает — и текст отказа говорит, что имя взято
из умолчания, а не названо в команде. Ресурсы уровня кластера, у которых namespace
нет по природе вида, областью не ограничиваются.

Выражение запроса область не трогает. Ограничение уходит в хранилище отдельным
параметром, предназначенным для сужения выдачи подмножеством логов, поэтому
выражение с конвейером остаётся работоспособным, а обойти ограничение вложенным
подзапросом нельзя: хранилище применяет его и к подзапросам.

Эхо каждого ответа называет применённые образцы (поле `namespaceScope`) и число
записей, не попавших в ответ из-за области (поле `recordsOutOfScope`). Выражение
запроса эхо показывает дословно таким, каким его дал пользователь.

**Область — это предохранитель от невнимательности, а не защита.** Права на чтение
namespace выдаёт кластер и Grafana, а не клиент: `namespaceScope` лишь сужает то,
что показывает инструмент, при уже имеющемся доступе. Обойти область можно правкой
`profile.json` или обращением к тем же данным сторонним клиентом — от этого поле
не защищает и не должно.

**Учётные данные нельзя передать аргументом команды.** Такого флага для логина,
пароля или токена нет и не будет: каждый вызов целиком попадает в журнал, и значение,
переданное аргументом, осталось бы там открытым текстом. Единственный источник
доступа — файл `credentials.json` профиля.

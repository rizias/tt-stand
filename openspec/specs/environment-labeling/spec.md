# environment-labeling Specification

## Purpose
Определение того, к какому окружению относится каждая полученная запись логов.
В хранилище лежат логи всех окружений сразу, поэтому вывод, сделанный не про то
окружение, выглядит правдоподобно и не содержит признаков ошибки.

## Requirements

### Requirement: Каждая запись несёт метку окружения

Инструмент SHALL сопровождать каждую возвращаемую запись логов именем окружения.
Окружение SHALL быть равно namespace записи. Никаких меток, псевдонимов, признаков
особого статуса и таблиц соответствий SHALL NOT существовать: продакшн является
таким же окружением, как остальные.

#### Scenario: Запись отнесена к окружению

- **WHEN** namespace записи определён
- **THEN** запись выводится с этим namespace в качестве имени окружения

#### Scenario: Сводка по окружениям

- **WHEN** команда вернула непустой список записей
- **THEN** ответ содержит сводку: сколько записей приходится на каждый namespace
  и сколько получило метку `unknown`

### Requirement: Два механизма определения окружения

Инструмент SHALL определять namespace записи двумя раздельными механизмами
в строгом порядке. **Сначала** проверяется поле `kubernetes.pod_namespace` записи:
если оно есть, окружение равно его значению, и дальше ничего не вычисляется.
**Только если этого поля нет**, namespace извлекается из значения upstream:
инструмент SHALL взять список namespace и выбрать тот, который является префиксом
строки upstream; при нескольких совпадениях SHALL выбираться самое длинное.

Обратный порядок недопустим: прикладная запись, чьё сообщение по форме похоже
на строку веб-трафика, иначе размечалась бы по upstream и получала бы `unknown`,
хотя namespace в самой записи присутствует.

Имена полей ответа хранилища SHALL читаться как плоские строковые ключи, содержащие
точки, а не как вложенные объекты.

#### Scenario: Запись лога приложения

- **WHEN** запись содержит `kubernetes.pod_namespace`
- **THEN** окружение равно этому значению

#### Scenario: Запись веб-трафика

- **WHEN** запись не содержит `kubernetes.pod_namespace`, но содержит значение
  upstream вида `<namespace>-<сервис>-<порт>`
- **THEN** окружение равно namespace из списка, являющемуся префиксом этого значения

#### Scenario: Есть оба поля сразу

- **WHEN** запись содержит и `kubernetes.pod_namespace`, и сообщение, разбираемое
  как строка веб-трафика с upstream
- **THEN** окружение равно значению `kubernetes.pod_namespace`, разбор upstream
  не выполняется

#### Scenario: Несколько namespace подходят как префикс

- **WHEN** сразу несколько namespace из списка являются префиксом одной строки upstream
- **THEN** выбирается самый длинный из них

#### Scenario: Ни одного пригодного поля

- **WHEN** запись не содержит ни `kubernetes.pod_namespace`, ни upstream
- **THEN** окружение равно `unknown`, а запись выводится целиком

### Requirement: Неизвестное окружение делает ответ неполным

Запись, для которой namespace не определился, SHALL получать метку `unknown`
и SHALL выводиться вместе с исходным значением поля, по которому определение
не удалось. Наличие хотя бы одной такой записи SHALL помечать ответ неполным.
Инструмент SHALL NOT достраивать namespace догадкой.

#### Scenario: Часть записей не размечена

- **WHEN** хотя бы одна возвращаемая запись получила метку `unknown`
- **THEN** ответ помечен неполным, а сводка называет число таких записей
  и перечисляет встреченные значения, по которым определение не удалось

#### Scenario: Upstream не совпал ни с одним namespace

- **WHEN** значение upstream не начинается ни с одного namespace из списка
- **THEN** окружение равно `unknown`, исходное значение upstream выводится рядом,
  а ответ помечен неполным

#### Scenario: Upstream является сетевым адресом

- **WHEN** значение upstream имеет вид сетевого адреса, а не имени вида
  `<namespace>-<сервис>-<порт>`
- **THEN** окружение равно `unknown`, а исходное значение выводится рядом

### Requirement: Список namespace запрашивается у хранилища без кэша

Список namespace SHALL запрашиваться у хранилища логов как множество значений поля
`kubernetes.pod_namespace`. Kubernetes для определения окружения SHALL NOT
требоваться. Запрос SHALL выполняться без границ периода и без лимита, чтобы список
не зависел от окна пользовательского запроса. Запрос SHALL выполняться только тогда,
когда среди полученных записей есть хотя бы одна строка ingress со значением upstream.
Кэширования списка SHALL NOT быть.

#### Scenario: Список получен из хранилища

- **WHEN** среди полученных записей есть строка ingress со значением upstream
- **THEN** инструмент запрашивает значения поля `kubernetes.pod_namespace`
  у хранилища логов и не обращается к Kubernetes

#### Scenario: Запрос списка не зависит от окна пользователя

- **WHEN** пользователь запросил логи за две минуты
- **THEN** список namespace запрашивается без границ периода и охватывает всю
  глубину хранения, а не эти две минуты

#### Scenario: Строк ingress нет

- **WHEN** среди полученных записей нет ни одной строки со значением upstream
- **THEN** список namespace не запрашивается, дополнительного обращения
  к хранилищу не происходит

#### Scenario: Список получить не удалось

- **WHEN** запрос списка namespace завершился отказом
- **THEN** команда всё равно возвращает полученные записи, помечает ответ неполным
  с отдельной причиной и называет недоступный источник

### Requirement: Команда env показывает список namespace и время его получения

Команда `env` SHALL показывать список namespace, известных хранилищу логов, и время
его получения. Признака кэширования SHALL NOT быть, поскольку кэша не существует.
Ручного заполнения и разметки в команде SHALL NOT быть.

#### Scenario: Просмотр списка

- **WHEN** пользователь вызывает `env`
- **THEN** ответ содержит список namespace и время его получения

#### Scenario: Повторный вызов

- **WHEN** пользователь вызывает `env` дважды подряд
- **THEN** каждый вызов обращается к хранилищу заново, признака кэша в ответе нет

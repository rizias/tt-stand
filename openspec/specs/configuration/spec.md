# configuration Specification

## Purpose

Хранение настроек инструмента у пользователя: расположение файла конфигурации, его
состав, создание и установка пакета. Репозиторий публичный, поэтому ничто, относящееся
к конкретной инсталляции, в него не попадает.

## Requirements

### Requirement: Конфигурация живёт вне репозитория

Файл конфигурации SHALL располагаться в домашнем каталоге пользователя.
Репозиторий и публикуемый пакет SHALL NOT содержать имён окружений, имён namespace,
значений upstream, адресов серверов и любых иных сведений о конкретной инсталляции —
ни в коде, ни в конфигурации по умолчанию, ни в тестах.

#### Scenario: Тесты не содержат внутренних сведений

- **WHEN** выполняются тесты проекта
- **THEN** они используют вымышленные имена окружений, namespace, upstream и адреса

#### Scenario: Путь конфигурации переопределяется

- **WHEN** пользователь задаёт путь к файлу конфигурации переменной окружения
  или аргументом команды
- **THEN** используется указанный файл, а не расположение по умолчанию

### Requirement: Состав конфигурации

Корневой файл настроек SHALL быть документом JSON. При размещении профилей в каталоге
`profiles` имя профиля по умолчанию SHALL задаваться полем `defaultProfile` корневого файла.
Настройки доступа и каталог журнала вызовов SHALL находиться в настройках соответствующего профиля.

Файл настроек профиля SHALL быть документом JSON. Настроек, за которыми нет
поведения, ни в корневом файле, ни в файле профиля SHALL NOT быть.

При размещении профилей в каталоге `profiles` путь файла учётных данных по умолчанию
SHALL указывать на `credentials.json` в каталоге соответствующего профиля.

#### Scenario: Конфигурация не разбирается

- **WHEN** файл конфигурации существует, но не является документом JSON
  либо не соответствует ожидаемой структуре
- **THEN** инструмент завершается с ненулевым кодом, классом ошибки `config_invalid`
  и называет, какое поле не прошло проверку

#### Scenario: Конфигурация отсутствует

- **WHEN** файла конфигурации нет в расположении по умолчанию, а путь к нему
  не задан ни аргументом `--config`, ни переменной окружения `TT_STAND_CONFIG`
- **THEN** значения полей корневого файла берутся по умолчанию

#### Scenario: Явно заданный файл конфигурации отсутствует

- **WHEN** путь к файлу конфигурации задан аргументом `--config` или переменной
  окружения `TT_STAND_CONFIG`, а файла по этому пути нет, и команда не является
  `config init`
- **THEN** инструмент завершается с ненулевым кодом и классом ошибки `config_invalid`,
  называя полный путь и источник, которым он задан; значения по умолчанию вместо
  явно названного файла SHALL NOT подставляться

#### Scenario: Учётные данные Grafana по умолчанию

- **WHEN** профиль размещён в каталоге `profiles` и путь к файлу учётных данных в его настройках не задан
- **THEN** он берётся из каталога этого профиля

#### Scenario: Список каталогов репозиториев задан не списком строк

- **WHEN** значение списка каталогов репозиториев не является списком строк
- **THEN** инструмент завершается с классом ошибки `config_invalid`
  и называет это поле

#### Scenario: Настройка времени жизни кэша не принимается

- **WHEN** в файле конфигурации задано время жизни кэша списка namespace
- **THEN** такой настройки не существует, поскольку кэша нет,
  и поведение инструмента от неё не зависит

### Requirement: Создание конфигурации не разрушает существующую

Команда `config init` без `--profile` SHALL создавать корневой файл настроек и профиль `default`:
каталог профиля, файл его настроек со значениями по умолчанию и пустой файл учётных
данных. Создаваемые файлы SHALL называть каждую настройку, у которой есть умолчание,
включая путь к файлу kubeconfig: по ним SHALL быть видно, откуда инструмент берёт
доступ к кластеру.

Таблиц соответствий окружений в них SHALL NOT быть: окружение равно namespace,
и список namespace берётся из хранилища логов. Существующие файлы SHALL NOT
перезаписываться без явного подтверждения.

#### Scenario: Файла нет

- **WHEN** настроек не существует и вызвана команда создания без `--profile`
- **THEN** создаются корневой файл и профиль `default`, а их пути названы в ответе

#### Scenario: Созданный файл называет источник доступа к кластеру

- **WHEN** профиль создан командой создания
- **THEN** его настройки содержат путь к файлу kubeconfig

#### Scenario: Созданный файл учётных данных пуст

- **WHEN** профиль создан командой создания
- **THEN** файл учётных данных существует и пуст, а ответ называет его путь
  и требуемый состав

#### Scenario: Файл существует, терминал доступен

- **WHEN** файл настроек существует, вызвана команда создания,
  и стандартный ввод подключён к терминалу
- **THEN** инструмент запрашивает подтверждение перезаписи; без подтверждения файлы
  не изменяются, команда завершается с кодом 0, а ответ называет существующие файлы
  и то, что они не изменены

#### Scenario: Файл существует, терминала нет

- **WHEN** файл настроек существует, вызвана команда создания без `--force`,
  и стандартный ввод не подключён к терминалу
- **THEN** инструмент не задаёт вопросов, не изменяет файлы, завершается с кодом 0,
  а ответ называет существующие файлы, то, что они не изменены, и флаг `--force`
  для перезаписи

#### Scenario: Файл создан другим процессом во время выполнения

- **WHEN** файла не было при проверке, но он появился до записи
- **THEN** файл не перезаписывается, команда завершается с ненулевым кодом
  и классом ошибки `config_exists`, называя этот файл

#### Scenario: Файл учётных данных не перезаписывается

- **WHEN** файл учётных данных профиля существует и не пуст, а вызвана команда
  создания с подтверждением перезаписи настроек
- **THEN** файл учётных данных остаётся без изменений

### Requirement: Установка пакета

Инструмент SHALL публиковаться как пакет npm с именем `@rizias/tt-stand` и SHALL
устанавливаться глобально средствами npm. Пакет SHALL объявлять требование
Node.js версии 22.19.0 или выше.

Продукт SHALL проверяться автоматически на Windows, Linux и macOS и SHALL
проверяться на объявленной минимальной версии Node.js.

Проверка типов SHALL охватывать исходники и все TypeScript-тесты со строгими настройками проекта. Ошибка типа в тесте SHALL приводить к ненулевому коду завершения `npm run check`.

#### Scenario: Запуск после глобальной установки

- **WHEN** пакет установлен глобально и команда вызвана по имени `tt-stand`
  в PowerShell либо в POSIX-совместимой оболочке
- **THEN** команда запускается и выводит результат в обеих оболочках

#### Scenario: Проверка продукта

- **WHEN** изменения попадают в основную ветку или предлагаются к слиянию
- **THEN** проверка типов, линтер, тесты и сборка выполняются на всех трёх
  операционных системах и на объявленной минимальной версии Node.js

#### Scenario: Ошибка типа в тесте

- **WHEN** TypeScript-тест содержит несовместимое присваивание или вызов
- **THEN** `npm run check` завершается с ошибкой и называет файл, строку и диагностическое сообщение

### Requirement: Профиль — единица настройки доступа

Настройки доступа SHALL группироваться в профиль. При размещении профилей в каталоге
`profiles` каждый профиль SHALL занимать отдельный каталог, имя которого SHALL быть именем профиля.
Каталог профиля SHALL содержать документ JSON с настройками профиля
и отдельный файл учётных данных. Настройки в корневом JSON-файле SHALL обрабатываться
согласно требованию «Настройки доступа в корневом JSON-файле».

Настройки профиля SHALL содержать: необязательный раздел доступа к Grafana
с базовым адресом, необязательным таймаутом HTTP-запроса в секундах, необязательным
явным идентификатором источника логов `grafana.datasourceUid` и необязательным
явным идентификатором источника метрик `grafana.metricsDatasourceUid`;
необязательный раздел доступа к кластеру с путём к kubeconfig и необязательным
именем контекста; необязательную область видимости namespace; необязательный
список каталогов с локальными копиями репозиториев; необязательный каталог журнала
вызовов с умолчанием внутри каталога профиля.

Базовый адрес Grafana SHALL находиться в настройках профиля, а не в файле
учётных данных: адрес не является секретом, и настройки профиля SHALL быть
пригодны к показу без раскрытия доступа.

#### Scenario: Профиль прочитан

- **WHEN** выбран профиль, каталог которого содержит настройки и учётные данные
- **THEN** команда выполняется с доступом этого профиля

#### Scenario: Настройки профиля не разбираются

- **WHEN** документ настроек профиля не является корректным JSON либо поле имеет
  неверный тип
- **THEN** инструмент завершается с ненулевым кодом и классом ошибки
  `config_invalid`, называя профиль и поле, не прошедшее проверку

#### Scenario: Источник метрик задан явно

- **WHEN** в профиле задано `grafana.metricsDatasourceUid`
- **THEN** команды метрик используют этот источник, а источник логов выбирается
  независимо от этой настройки

#### Scenario: Идентификатор источника задан пустой строкой, «.» или «..»

- **WHEN** `grafana.datasourceUid` или `grafana.metricsDatasourceUid` в профиле
  задан пустой строкой, значением `.` или значением `..`
- **THEN** инструмент завершается с ненулевым кодом и классом ошибки
  `config_invalid`, называя профиль и это поле — такое значение нельзя
  закодировать сегментом пути `/api/datasources/proxy/uid/<uid>/`, а не считает
  настройку незаданной

### Requirement: Выбор профиля

Действующий профиль SHALL определяться в порядке: аргумент команды, затем переменная
окружения, затем имя профиля по умолчанию из корневого файла настроек. Если ни один
из источников профиль не назвал, а профиль в установке ровно один, SHALL
использоваться он.

Выбор профиля SHALL NOT зависеть от формы записи аргумента: значение, отделённое
пробелом, и значение, записанное через знак равенства, SHALL давать один и тот же
профиль. Это SHALL относиться и к аргументу пути к файлу настроек.

Действующий профиль SHALL быть один на весь вызов: всё, что зависит от профиля,
включая каталог журнала вызовов, SHALL определяться этим же профилем.

Если профиль не назван ни одним источником, а профилей несколько, инструмент SHALL
завершаться с ненулевым кодом и классом ошибки `profile_ambiguous`, перечисляя
имена профилей и называя способы выбрать один.

Если названный профиль не существует, инструмент SHALL завершаться с ненулевым кодом
и классом ошибки `profile_missing`, называя запрошенное имя и перечисляя имеющиеся.

#### Scenario: Профиль задан аргументом

- **WHEN** профиль назван и аргументом команды, и переменной окружения
- **THEN** используется профиль из аргумента

#### Scenario: Профиль задан переменной окружения

- **WHEN** аргумент профиля не задан, а переменная окружения названа профиль
- **THEN** используется профиль из переменной окружения

#### Scenario: Форма записи аргумента не влияет на выбор

- **WHEN** один и тот же профиль назван записью через пробел и записью через знак
  равенства
- **THEN** оба вызова работают с одним профилем, и запись журнала обоих попадает
  в каталог журнала этого профиля

#### Scenario: Профиль в установке единственный

- **WHEN** профиль не назван ни одним источником и профиль в установке ровно один
- **THEN** используется этот профиль

#### Scenario: Профиль не выбран, а их несколько

- **WHEN** профиль не назван ни одним источником и профилей несколько
- **THEN** класс ошибки `profile_ambiguous`, а текст перечисляет имена профилей

#### Scenario: Названного профиля нет

- **WHEN** назван профиль, каталога которого не существует
- **THEN** класс ошибки `profile_missing`, а текст называет запрошенное имя
  и перечисляет имеющиеся

### Requirement: Профиль может описывать не весь доступ

Профиль SHALL быть пригодным, если описывает только доступ к Grafana, только доступ
к кластеру либо и то, и другое. Команда, которой нужна не описанная в профиле часть,
SHALL завершаться с ненулевым кодом и классом ошибки `profile_incomplete`, называя
профиль и отсутствующую часть.

Инструмент SHALL NOT восполнять отсутствующую часть настройками другого профиля,
умолчанием или переменной окружения: доступ одного контура SHALL NOT смешиваться
с доступом другого.

#### Scenario: В профиле нет доступа к кластеру

- **WHEN** выбран профиль без раздела доступа к кластеру и вызвана команда,
  обращающаяся к кластеру
- **THEN** класс ошибки `profile_incomplete`, а текст называет профиль
  и отсутствующую часть

#### Scenario: В профиле нет доступа к Grafana

- **WHEN** выбран профиль без раздела доступа к Grafana и вызвана команда логов
- **THEN** класс ошибки `profile_incomplete`, а текст называет профиль
  и отсутствующую часть

#### Scenario: Отсутствующая часть не подменяется

- **WHEN** в профиле нет доступа к кластеру, а в другом профиле он есть
- **THEN** инструмент не использует доступ другого профиля

### Requirement: Настройки доступа в корневом JSON-файле

Если в каталоге `profiles` рядом с корневым файлом нет каталогов профилей, а корневой JSON
содержит `grafana`, `kubernetes` или `repositoryRoots`, инструмент SHALL читать этот файл
как единственный доступный профиль `default`. Выбор профиля SHALL подчиняться требованию
«Выбор профиля».

Путь доступа Grafana SHALL определяться полем `grafana.credentialsFile`.
При отсутствии этого поля SHALL использоваться `~/.tt-stand/.grafana-ro`.

#### Scenario: Настройки доступа находятся в корневом файле

- **WHEN** корневой JSON содержит `grafana`, каталоги профилей отсутствуют
  и выбран профиль `default`
- **THEN** команды используют настройки из корневого файла, а эхо называет профиль `default`

### Requirement: Учётные данные не принимаются аргументом командной строки

Инструмент SHALL NOT предоставлять способа передать логин, пароль или токен
доступа к Grafana аргументом команды или переменной окружения. Значения доступа
SHALL читаться только из файла учётных данных профиля.

#### Scenario: Попытка передать доступ аргументом

- **WHEN** команда вызвана с неизвестным флагом для передачи логина, пароля или токена
- **THEN** инструмент завершается с классом ошибки `bad_request` и подсказкой `tt-stand --help`,
  значения аргументов исключены из ответа и журнала

#### Scenario: Журнал не содержит значений доступа

- **WHEN** выполнена любая команда, обращающаяся к Grafana
- **THEN** журнал содержит вызов и ответ по общему контракту журналирования
  и исключает значения учётных данных, загруженные инструментом для подключения

### Requirement: Команда перечисления профилей

Инструмент SHALL предоставлять команду, перечисляющую профили установки. Для каждого
профиля ответ SHALL называть: имя, наличие доступа к Grafana, наличие доступа
к кластеру, наличие области видимости и признак профиля по умолчанию.

Ответ SHALL называть состояние файла учётных данных каждого профиля тремя
различимыми положениями: файла нет, файл есть и пуст, файл есть и заполнен.
Команды `config profiles` и `config --json` SHALL позволять агенту узнать состояние доступа через инструмент.
Ответ `config profiles` SHALL содержать число найденных профилей в `summary.profileCount`.

Ответ SHALL NOT содержать значений учётных данных: ни логина, ни пароля, ни токена.

Команда SHALL отрабатывать и тогда, когда профилей нет: ответ SHALL быть пустым
перечнем, а не отказом.

#### Scenario: Профили перечислены

- **WHEN** вызвана команда перечисления и профили существуют
- **THEN** ответ называет каждый профиль, состав его доступа и профиль по умолчанию

#### Scenario: Учётные данные не раскрываются

- **WHEN** вызвана команда перечисления
- **THEN** ответ не содержит логина, пароля и токена ни одного профиля

#### Scenario: Состояние файла учётных данных

- **WHEN** вызвана команда перечисления, а файл учётных данных профиля существует
  и пуст
- **THEN** ответ различает это положение и от отсутствия файла, и от заполненного
  файла, не раскрывая содержимого

#### Scenario: Профилей нет

- **WHEN** вызвана команда перечисления и профили не обнаружены ни в каталоге `profiles`,
  ни в корневом JSON-файле
- **THEN** ответ содержит пустой перечень, признак отказа не выставляется,
  а код завершения нулевой

### Requirement: SSH и MongoDB в профиле

Профиль SHALL поддерживать именованные записи `servers` только с видами `ssh` и `mongodb`.
Сервер MongoDB SHALL ссылаться на SSH-сервер по имени и MAY задавать `defaultDatabase`.
Настройки Grafana и Kubernetes SHALL читаться из разделов `grafana` и `kubernetes`.
`--config` и `TT_STAND_CONFIG` SHALL выбирать общий файл конфигурации.

#### Scenario: MongoDB, Grafana и Kubernetes в одном профиле

- **WHEN** профиль содержит записи `servers` видов `ssh` и `mongodb` и разделы `grafana` и `kubernetes`
- **THEN** MongoDB использует записи `servers`, Grafana использует `grafana`, Kubernetes использует `kubernetes`

#### Scenario: Общий файл задан аргументом или переменной окружения

- **WHEN** пользователь передаёт общий `config.json` через `--config` или `TT_STAND_CONFIG`
- **THEN** каталог `profiles` определяется рядом с этим файлом,
  а выбор профиля выполняется согласно требованию «Выбор профиля»

#### Scenario: MongoDB в корневом JSON-файле

- **WHEN** каталоги профилей отсутствуют, корневой JSON содержит `grafana` и `servers` с MongoDB
  и передан через `--config` либо `TT_STAND_CONFIG`
- **THEN** инструмент обнаруживает профиль `default` с этими настройками,
  файл доступа Grafana определяется `grafana.credentialsFile` или его умолчанием,
  а профиль выбирается согласно требованию «Выбор профиля»

### Requirement: Настройки SSH и MongoDB

Для подключения SSH-сервер SHALL задавать host, username и privateKeyPath. Поля port, knownHostsPath и timeoutSeconds MAY задаваться. Порт по умолчанию SHALL быть 22, knownHostsPath по умолчанию SHALL быть ~/.ssh/known_hosts. Для подключения сервер MongoDB SHALL задавать uri и sshServer. Поля defaultDatabase и timeoutSeconds MAY задаваться. Таймаут по умолчанию SHALL быть 30 секунд. Значение timeoutSeconds SHALL быть конечным числом больше нуля и не больше 2147483.647 секунды. Таймаут SSH SHALL ограничивать установление SSH-подключения, таймаут MongoDB SHALL ограничивать весь вызов, включая подключение и чтение. Необязательная база SHALL переопределяться флагом --database на один вызов. Несколько MongoDB-серверов SHALL требовать явного --server.

#### Scenario: База по умолчанию

- **WHEN** вызов mongo не содержит --database, а сервер задаёт defaultDatabase
- **THEN** команда использует defaultDatabase и называет её в echo

#### Scenario: Выбранный SSH-сервер отсутствует

- **WHEN** sshServer не соответствует записи вида ssh
- **THEN** команда возвращает ошибку конфигурации до подключения

### Requirement: Секреты MongoDB и SSH в файле доступа

Инструмент SHALL читать секреты MongoDB и SSH из `credentials.json` рядом с профилем по именам серверов.
Запись SSH MAY содержать `passphrase`, запись MongoDB MAY содержать `username` и `password`.
Путь приватного ключа SHALL находиться в профиле.

#### Scenario: Заполненный MongoDB-профиль

- **WHEN** владелец указал пути ключа и known_hosts и заполнил записи доступа
- **THEN** команда mongo читает эти файлы внутри процесса инструмента и выполняет SSH-подключение

### Requirement: Конфигурация проверяется безопасной командой

Команда config --json SHALL показывать эффективные несекретные настройки и признаки заданности секретов. Поле defaultProfile SHALL именоваться профилем по умолчанию в справке и ответах. Чтение настроек SHALL использовать значения профиля и умолчания соответствующих полей.

#### Scenario: Агент проверяет конфигурацию

- **WHEN** агент вызывает config --json
- **THEN** ответ содержит признаки заданности доступа и исключает значения секретов

#### Scenario: Адрес Grafana содержит userinfo

- **WHEN** адрес Grafana содержит логин или пароль в userinfo и вызвана config --json
- **THEN** userinfo отсутствует в значениях ответа, описании источников полей и журнале

#### Scenario: Посторонние переменные окружения

- **WHEN** окружение содержит TT_STAND_SERVER_*, TT_STAND_DESCRIPTION или TT_STAND_JOURNAL_DIRECTORY
- **THEN** настройки серверов, секреты и каталог журнала выбираются из профиля и установленных умолчаний

#### Scenario: Неизвестная команда конфигурации

- **WHEN** вызвана неизвестная подкоманда config
- **THEN** ответ содержит bad_request, а общий файл не изменяется

### Requirement: Именованное создание профиля

Команда config init с явным --profile SHALL создавать названный профиль. Если общий файл отсутствует, команда SHALL записывать его имя в defaultProfile. При существующем общем файле команда SHALL сохранять его содержимое. Перезапись существующего профиля SHALL требовать подтверждения либо --force. Файл доступа SHALL сохраняться при любом режиме повторного создания.

#### Scenario: Первый профиль имеет явное имя

- **WHEN** файлов настройки нет и вызвана config init --profile investigation
- **THEN** создаётся профиль investigation и общий файл с defaultProfile investigation

#### Scenario: Добавление второго профиля

- **WHEN** общий файл уже содержит defaultProfile default и вызвана config init --profile investigation для отсутствующего профиля
- **THEN** создаётся investigation, а профиль по умолчанию остаётся default

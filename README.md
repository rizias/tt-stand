# tt-stand

Консольный инструмент только для чтения: логи окружений из VictoriaLogs через Grafana,
разбор HTTP-трафика и токенов, состояние Kubernetes без `kubectl`, определение namespace
окружений и честный отчёт о полноте результата. Инструмент снимает механику доступа
и разбора, но не решает за пользователя: не порождает вариантов искомого значения,
не режет период, не подставляет лимитов и таймаутов, не сортирует записи и ничего
не скрывает. Порядок расследования — в скилле `skills/tt-stand/SKILL.md`.

## Установка

```text
npm install -g @rizias/tt-stand
```

Нужен Node.js 22.19.0 или выше. Поддерживаются Windows, Linux и macOS, PowerShell
и POSIX-совместимые оболочки. Клиент Kubernetes встроен, `kubectl` не нужен.

> [!NOTE]
> В PowerShell при политике выполнения `Restricted` обёртка `.ps1` не запускается.
> Вызовите `tt-stand.cmd`, она политикой не ограничена, либо один раз выполните
> `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned`. Подробно — в
> [docs/install.md](docs/install.md).

## Быстрый старт

```text
tt-stand config init
```

Команда создаёт `~/.tt-stand/config.json` и профиль `default`. Дальше два файла профиля
заполняются вручную, инструмент за вас их не придумывает:

1. `~/.tt-stand/profiles/default/profile.json` — вписать адрес Grafana полем
   `grafana.baseUrl`. Без него любая команда логов отвечает `profile_incomplete`.
2. `~/.tt-stand/profiles/default/credentials.json` — вписать доступ: логин с паролем
   либо токен.

Проверка и первый поиск:

```text
tt-stand config profiles
tt-stand env
tt-stand logs search --value "<искомое значение>" --start -2d --end now
```

`config profiles` показывает, что в профиле настроено, не раскрывая значений; `env`
проверяет доступ к Grafana и показывает namespace окружений.

## Настройка

Всё, что относится к инструменту, лежит в каталоге `~/.tt-stand`:

```text
~/.tt-stand/
  config.json                      корневые настройки
  profiles/<имя>/profile.json      настройки профиля
  profiles/<имя>/credentials.json  учётные данные профиля
  profiles/<имя>/journal/          журнал вызовов профиля
```

Профиль — связка «Grafana и кластер», к которой обращаются по имени: по одному на контур,
филиал или стенд. Действующий профиль выбирается флагом `--profile`, иначе переменной
`TT_STAND_PROFILE`, иначе полем `defaultProfile` корневого файла. Если профиль один, он
берётся без указания; если их несколько и выбора нет — отказ `profile_ambiguous`,
молчаливого выбора не бывает.

Поля `profiles/<имя>/profile.json`:

| Поле | Тип | Умолчание | Что делает |
|---|---|---|---|
| `grafana.baseUrl` | строка, URL | нет | базовый адрес Grafana |
| `grafana.credentialsFile` | строка, путь | `credentials.json` в каталоге профиля | файл с доступом к Grafana |
| `grafana.timeoutSeconds` | число > 0 | нет | таймаут одного HTTP-запроса; без него таймаута нет вовсе |
| `grafana.datasourceUid` | строка | нет | закрепить источник логов; без поля берётся первый подходящий, остальные названы в пояснении ответа |
| `kubernetes.kubeconfig` | строка, путь | нет | путь к kubeconfig, может вести в каталог |
| `kubernetes.context` | строка | контекст, объявленный в kubeconfig действующим | имя контекста при нескольких кластерах |
| `namespaceScope` | список строк | нет, ограничения нет | образцы имён namespace, которые инструмент показывает |
| `repositoryRoots` | список строк, пути | пусто | родительские каталоги, внутри которых лежат репозитории с именами образов; заполняется по желанию — без него `image` отдаёт версию и SHA из тега, но не ветки |
| `journal.directory` | строка, путь | каталог `journal` внутри профиля | каталог журнала вызовов профиля |

Доступ хранится отдельно, в `credentials.json` профиля: `kind: "basic"` с полями `login`
и `password` либо `kind: "token"` с полем `token`. Учётные данные нельзя передать аргументом
команды: каждый вызов попадает в журнал целиком, и значение осталось бы там открытым текстом.

Профили, совместимость со старым файлом настроек, выбор kubeconfig и область видимости
namespace — в [docs/configuration.md](docs/configuration.md).

## Команды

| Команда | Что делает |
|---|---|
| `logs query --query <LogsQL> --start <время> --end <время> [--limit N]` | произвольный запрос к хранилищу логов |
| `logs search --value <значение> [--value ...] --start <время> --end <время> [--limit N]` | поиск строк по одному или нескольким значениям |
| `logs http [--query <LogsQL> \| --value <значение> ...] --start <время> --end <время> [--limit N]` | то же плюс разбор строки веб-трафика и раскрытие токенов |
| `logs fields --field <имя поля> --start <время> --end <время> [--query <LogsQL>] [--limit N]` | какие значения встречаются у поля |
| `token [--value <строка>]` | раскрыть токен: заголовок, полезная нагрузка, сроки |
| `k8s pods [--namespace <ns>]` | что запущено, сколько раз перезапускалось, с каким образом |
| `k8s log <под> [--namespace <ns>] [--container <имя>] [--previous]` | вывод приложения; `--previous` — вывод упавшего запуска |
| `k8s events [--namespace <ns>]` | что кластер сообщал об окружении |
| `k8s history <рабочая нагрузка> [--namespace <ns>]` | история выкаток: версии, время, образы |
| `k8s get <ресурс> [--namespace <ns>] [--name <имя>]` | чтение любого объекта кластера, если он разрешён учётной записи |
| `image <имя-образа:тег>` | коммит по образу: автор, дата, сообщение, ветки-кандидаты |
| `env` | namespace окружений из хранилища логов |
| `config init [--force]` | создать корневой файл настроек и профиль `default` |
| `config profiles` | что настроено в профилях, без раскрытия значений |
| `init [путь к проекту] [--for claude,agents]` | разложить скилл агентам в проект |
| `update` | обновить пакет до последней опубликованной версии |

Общие флаги: `--human` — человекочитаемый вывод вместо JSON; `--config <путь>` — другой файл
настроек; `--profile <имя>` — профиль доступа, иначе `TT_STAND_PROFILE`, иначе `defaultProfile`
из корневого файла. Время принимается как RFC 3339 или относительно, например
`--start -2d --end now`; значения уходят в хранилище как даны.

Зачем нужна каждая команда, что лежит в её ответе и какие права нужны в кластере —
в [docs/commands.md](docs/commands.md).

## Контракт вывода

Каждый ответ — один документ JSON:

- `ok` и `command`;
- `data` — данные без скрытия, замены и обрезки;
- `summary` — сводка команды;
- `echo` — что фактически выполнено: выражение, период, лимит, упор в лимит, число нечитаемых
  строк, порядок сервера, применённая область видимости, путь записи журнала;
- `incomplete` и `incompleteReasons` — полон ли результат и почему нет;
- `errorClass` и `error` — машиночитаемый класс и русское объяснение отказа.

Отказ печатается в тот же стандартный вывод и тем же конвертом:

```json
{
  "ok": false,
  "command": "logs query --start -2d --end now",
  "data": null,
  "incomplete": true,
  "incompleteReasons": ["команда не отработала: данные не получены"],
  "errorClass": "bad_request",
  "error": "Не задан обязательный параметр --query."
}
```

Код завершения `0` означает, что команда отработала, включая пустой или неполный результат.
Ненулевой код означает отказ.

> [!IMPORTANT]
> Пустой результат при `incomplete: true` не означает «ничего не было».

Полный состав ответа, примеры в обоих режимах и устройство журнала вызовов —
в [docs/output.md](docs/output.md).

## Классы ошибок

| Класс | Значение |
|---|---|
| `bad_request` | команда или сочетание аргументов некорректно |
| `credentials_missing`, `credentials_incomplete` | нет файла Grafana или обязательной строки |
| `auth_failed`, `datasource_list_forbidden`, `datasource_not_found` | отказ авторизации или поиска источника Grafana |
| `timeout_client`, `upstream_error`, `stream_aborted` | запрос логов не завершён штатно |
| `config_invalid`, `config_exists` | конфигурация некорректна или защищена от перезаписи |
| `profile_missing`, `profile_ambiguous` | профиль не найден или не назван, когда профилей несколько |
| `profile_incomplete` | в профиле нет части настроек, нужной вызванной команде |
| `namespace_out_of_scope` | запрошенный namespace не входит в область видимости профиля |
| `token_invalid` | compact JWT/JWS, header или payload не разобран |
| `kubeconfig_missing`, `kubeconfig_ambiguous`, `kubeconfig_invalid` | kubeconfig отсутствует, неоднозначен или некорректен |
| `kube_context_missing` | нет действующего контекста или связанного кластера |
| `k8s_access_forbidden` | RBAC запретил чтение |
| `k8s_resource_not_found`, `k8s_resource_ambiguous` | ресурс discovery не найден или неоднозначен |
| `k8s_upstream_error` | иной отказ Kubernetes API или транспорта |
| `pod_not_found` | выбранный под отсутствует |
| `git_unavailable` | git не найден в PATH |
| `skill_copy_skipped` | часть копий скилла не поставлена; причины по каждой копии в `data.skipped` |
| `update_failed` | npm не смог обновить пакет; его код и вывод в `data` |
| `previous_log_unavailable` | лог предыдущего запуска уже утрачен |

## Скилл для агента

Скилл едет в пакете: `skills/tt-stand/SKILL.md`. В нём порядок расследования: проверка
полноты, варианты искомого значения, разворот «значение → идентификатор», связь HTTP-разбора
с токеном, чтение состояния Kubernetes. Разложить его агентам — команда `init`:

```text
tt-stand init                       # спросит, куда ставить, в текущем проекте
tt-stand init C:\путь --for claude  # без вопроса: только .claude/skills/
```

| Каталог | Кто читает |
|---|---|
| `.claude/skills/` | Claude Code |
| `.agents/skills/` | Codex, OpenCode |

Команда показывает полный список путей и до подтверждения не создаёт ни одного файла; во все
каталоги сразу не ставит никогда. Глобальной установки нет — скилл живёт в проекте. Места
установки запоминаются в `~/.tt-stand/skills-registry.json`; после обновления пакета копии
обновляются сами при следующем запуске любой команды, а файлы, добавленные рядом со скиллом
вручную, не трогаются. Ответ `init` — тот же документ JSON, что у остальных команд:
поставленные и пропущенные копии названы в `data`.

Любому другому агенту файл передаётся как системная инструкция или прикладывается к запросу
целиком: текст самодостаточен, внешних ссылок и подстановок в нём нет. Скилл описывает, как
пользоваться инструментом, но ничего в нём не включает и не выключает: без скилла все команды
работают так же. Порядок первичной настройки для того, кто устройством профилей не знаком,
тоже лежит в скилле — агент по нему помогает настроить инструмент, а логин, пароль или токен
человек вписывает в файл учётных данных своими руками.

О новой версии пакета инструмент сообщает раз в сутки при выводе в терминал; обновление —
`tt-stand update`, код завершения равен коду npm.

## Разработка

```text
npm ci
npm run check
```

`npm run check` — проверка типов, линтер, поиск неиспользуемого кода, предел размера
файлов, тесты и сборка. Она же выполняется в сборочной проверке и перед публикацией.
`npm install` заодно включает git-хуки: перед коммитом проверяются линтер, размер файлов
и секреты, перед отправкой — весь `npm run check`.

# Правила работы в этом репозитории

Относятся ко всем агентам: Claude Code, Codex, воркеры делегатора и любые другие.

## Коммиты

Сообщение коммита пишется по существу изменения: что изменилось и зачем.

## Постановка задачи

Действующие требования — в `openspec/specs/`. Это единственный источник: что инструмент
обязан делать, читать там, а не в коде и не в README.

Работа над ТЗ идёт в два этапа: сначала вопросы владельцу, после письменных ответов —
артефакты. Не решай за владельца ничего, что он не решил.

## Язык

Артефакты, комментарии и обсуждение — на русском. Структурные заголовки OpenSpec
и ключевые слова SHALL/MUST — на английском.

## Технические ограничения

- TypeScript / Node. **Python в проекте не используется.**
- Инструмент не выполняет изменяющих запросов к внешним системам.
- В репозиторий не попадает ничего внутреннего: ни учётных данных, ни имён окружений,
  namespace, upstream и адресов конкретной инсталляции. Вывод инструмента при этом
  ничем не ограничивается: данные отдаются как есть.

## Команды

- `npm ci` — зависимости; `npx lefthook install` — git-хуки (`npm install` ставит их сам).
- `npm run check` — типы, линт, форматирование, knip, тесты, сборка. Единственная мера
  готовности; запускай перед коммитом и перед публикацией.
- `npm run build` — `tsc` → `dist/`; `npx vitest run test/<файл>.test.ts` — один файл тестов.
- `openspec validate --specs --strict` — проверка действующих спецификаций.

`npm run check` выполняется в CI и перед публикацией. Перед коммитом git-хуки
проверяют линтер и форматирование, а при установленном `gitleaks` — также секреты.
Перед отправкой выполняется весь `npm run check`.
Устройство кода описано в [docs/architecture.md](docs/architecture.md).

## Стиль кода

- Комментариев в коде нет: ни однострочных, ни блочных, ни JSDoc. Исключения — shebang,
  директивы инструментов и маркер `owner:` по прямой просьбе владельца. Проверяет правило
  `local/no-comments` из `eslint.config.mjs`; директивы `eslint-disable` запрещены.
- Функция сложнее 15 по правилу `complexity` — ошибка. Замороженные в
  `eslint-suppressions.json` функции только убывают: `npm run lint` убирает ненужные
  подавления, руками файл не правится.
- Prettier форматирует код и артефакты с шириной 120 символов. ESLint проверяет
  `@stylistic/max-len`. Прежние длинные литералы заморожены средствами ESLint,
  существующие подавления только убывают.
- Мёртвого кода нет: `knip` в `npm run check` это проверяет.
- `scripts/`, `eslint.config.mjs` и `src/skills/updater*.ts` — копии общего шаблона,
  локально не правятся.

## Ведение работ

Через OpenSpec (схема `spec-driven`). Артефакты обязаны проходить валидацию OpenSpec.
В репозитории хранятся только действующие спецификации в `openspec/specs/`.
Каталог `openspec/changes/` и архив завершённых изменений не коммитятся.

Агент получает настройки через `tt-stand config --json` и проверяет подключение
командами tt-stand. Прямое чтение пользовательских профилей, файлов учётных данных
и приватных SSH-ключей запрещено. Заполненный профиль и ключ изменяются только
по прямой просьбе владельца. Автотесты используют искусственные данные и свои ключи.

## Выпуск

Записи копятся в `CHANGELOG.md` в разделе «Не выпущено». Выпуск — Actions → Release →
patch/minor/major. Дальше CI сам проверяет, поднимает версию, ставит метку, публикует
в npm и создаёт запись в GitHub Releases.
